# Sehaty — specification

**صحتي / sehat — "my health".** A personal health agent: training, food, weight, in
Indonesian or English, reachable by voice, photo, chat or dashboard.

Written 10 Sep 2026 from a design conversation between Raka Satria and Claude Code.
Decisions marked **DECIDED** were made explicitly; everything else is derived from them.

---

## 1. What it is

One backend serving several front doors. The backend is an **MCP server**; the front doors
are whatever can speak to it.

```
        voice note ─┐
        meal photo ─┤
        chat        ├─→  Telegram (Hermes telegram-platform)  ─┐
                    │                                          ├─→  Sehaty MCP  ─→ SQLite
        WhatsApp ───┴─→  Chief → sehaty profile (Hermes)      ─┘        ↑
                                                                        │
        browser ────────→ sehaty.homedev.app (Cloudflare Access) ───────┘
```

**DECIDED:** the MCP server is the only thing that touches data. Every front door is a
client. That is what makes one deployment serve Raka on WhatsApp and other people on
Telegram without a second codebase.

## 2. Decisions taken

| | decision | why |
|---|---|---|
| **Language** | **Go** — official `modelcontextprotocol/go-sdk` | single static binary, no venv, trivial systemd deploy, and Go 1.27.1 is already on all three dev boxes. The Python prototype hit a real wall: the Mac's system Python is 3.9 and the SDK needs ≥3.10. |
| **Encryption** | **server holds the key** | Sehaty must be able to message people unprompted — weekly reviews, "you haven't logged in five days". That is impossible if only the user can decrypt. **Stated honestly: this protects backups and a stolen disk, NOT a compromised running server.** |
| **Storage** | structured SQLite, row-level isolation | the alternative considered was encrypted Markdown blobs; rejected because "how has my weight moved over six months" then means decrypting and parsing everything, and SQL is exactly the tool for that question |
| **Ports** | MCP and dashboard on **separate** ports | MCP is a tool-execution surface. Only the dashboard gets published; the tool surface never leaves the LAN. |
| **Dataset** | git submodule | 169 MB stays upstream; only a pointer is committed. Its licence is `NOASSERTION`, so it must not be redistributed. |
| **Name** | `sehaty` agent, `gym-buddy` MCP repo | the agent is broader than the gym |

## 3. Data model

One SQLite database. Every row belongs to a profile; every query is filtered by
`profile_id` in a single data-access layer that nothing bypasses. **That isolation — not
encryption — is what stops one person seeing another's data.**

```
profile(id, name, equipment_json, goal, sessions_per_week, session_minutes,
        experience, max_difficulty, locale, created_at)

identity(channel, external_id, profile_id)        -- the multi-front-door join
    telegram   8412…      → raka
    access     raka@…     → raka
    mcp        <api key>  → raka

training_log(id, profile_id, date, exercise, body_part, sets, reps, weight_kg, volume_kg, note)
cardio_log(id, profile_id, date, minutes, speed_kmh, incline_pct, distance_km, note)
weight_log(id, profile_id, date, weight_kg, note)
food_log(id, profile_id, date, meal, item, grams, kcal, protein_g, carbs_g, fat_g,
         source, photo_hash)
secret_blob(profile_id, key, ciphertext)          -- free text only: notes, diet plans
```

**Identity is asked once.** A Telegram `user_id` cannot be spoofed while the bot token is
safe; Cloudflare Access supplies a verified email header. Both resolve to one `profile_id`,
after which the person is never asked "who are you?" again.

**Encryption is selective.** Numbers stay in plain columns because the dashboard, the
reminders and every query need them. Free text a clinician wrote — the diet plan, notes —
goes in `secret_blob`, AES-GCM, key from `SEHATY_KEY` in the environment. This protects the
NAS backups and a stolen container image. It does not protect a live compromised server,
and the documentation must not pretend otherwise.

## 4. Bahasa Indonesia

**Not a translation layer bolted on — a first-class requirement.**

- The **exercise dataset has 10 languages and Indonesian is not one of them.** Exercise
  names and instructions must be translated on demand and cached, never re-translated per
  request.
- **Open Food Facts is thin on Indonesian food.** `nasi uduk`, `tempe orek`, `soto ayam`
  will not resolve. An AI-estimation path is required, and **must be labelled an estimate**
  in the log (`source='ai_estimate'`) so it is never confused with measured data.
- Raka's nutritionist prescription is written in Indonesian and uses **Satuan Penukar**
  (the exchange-unit system) — `1P` means a portion, not a weight. Any adherence check must
  understand exchanges, not just grams.
- `profile.locale` drives replies. Mixed input is normal and must not break anything —
  Indonesians code-switch mid-sentence.

## 5. Voice and photo

**Voice.** A voice note is the natural way to log between sets. Telegram delivers OGG;
transcribe, then parse the transcript into a structured entry.

> *"tadi squat tiga set dua belas kali pakai dua puluh kilo"*
> → `log_set(exercise="goblet squat", sets=3, reps=12, weight_kg=20)`

**It must confirm before writing.** A misheard "dua puluh" as "dua belas" silently corrupts
the record, and a training log is only worth anything if it is true.

**Photo.** A meal photograph goes to a vision model, which identifies the dish and
estimates portion and macros.

- Always logged as `source='ai_estimate'` with the photo hash retained.
- **Estimates are shown as ranges, never false precision.** "roughly 550-700 kcal" is
  honest; "612 kcal" from a photograph is not.
- Indonesian dishes are the main use case, which is precisely where Open Food Facts fails.

## 6. Tool surface

**Deterministic** — no model call, no cost, same answer every time:
`list_profiles` · `create_profile` · `get_profile` · `find_exercises` · `plan_session` ·
`cardio_protocol` · `log_set` · `log_cardio` · `log_weight` · `lookup_food` · `log_food` ·
`progress` · `diet_adherence`

**AI-backed** — via OpenRouter, and they **fail loudly without a key** rather than
degrading into something that reads like advice but is a guess:
`coach_review` · `adapt_session` · `explain_exercise` · `parse_voice_log` ·
`estimate_meal_photo` · `translate_exercise`

The split is structural, not a convention. A tool that sometimes calls a model and
sometimes does not is impossible to reason about and impossible to price.

## 7. Safety — non-negotiable

- **Never diagnose.** Sharp, joint-centred, radiating or persistent pain gets "this needs a
  professional", and programming around it stops.
- **Never prescribe unavailable equipment.** The filter runs before selection and has no
  override at prescribe time. A plan someone cannot perform is worse than no plan.
- **Respect `max_difficulty`.** The dataset happily returns pistol squats and korean dips;
  the prototype prescribed exactly those to a beginner. The dataset has **no difficulty
  field**, so one must be derived once by an LLM, cached, and committed.
- **Never invent a number.** Not a calorie, not a weight, not a session that did not happen.
- **Missing sessions is not failure** and must never be framed as such. Guilt makes people
  stop.
- **Never comment on anyone's body** unless they raise it, and then only from the log.

## 8. Build and deployment

**DECIDED 10 Sep: build on `hrmdev01`, run on `srvdev01`.** The dev box has the toolchain
and `gh`; the server box runs services. Neither does the other's job.

```
hrmdev01   10.254.1.104   Go 1.27.1, gh (rakasatria)   source of truth, builds, tests
srvdev01   10.254.1.105   Debian 12                    runs the binary
```

Go produces a single static binary, so deployment is `scp` plus a systemd restart — no
runtime, no venv, no dependency drift between the two machines. That property is most of
why Go was chosen.

```
srvdev01:8765  MCP        LAN only, never published   hermes mcp add --url
srvdev01:8766  dashboard  published                   sehaty.homedev.app
```

Published with `publish.py add --host sehaty.homedev.app --service
http://10.254.1.105:8766 --access`. That tool **refuses to publish without Cloudflare
Access or an explicit `--public`** — the correct default for health data.

**Cloudflare terminates TLS**, so Cloudflare can see the traffic. Normal for a fitness
dashboard, but the user's choice to make knowingly.

## 8b. Media storage — pluggable

Voice notes and meal photos need somewhere to live. **DECIDED: a storage interface with two
implementations.** Raka's own server uses `local`. `s3` exists because this is going out to
a community, and not everyone runs a box with a disk they control.

```go
type MediaStore interface {
    Put(ctx context.Context, hash string, r io.Reader) (string, error)
    Get(ctx context.Context, hash string) (io.ReadCloser, error)
    Exists(ctx context.Context, hash string) (bool, error)
}
```

| backend | config | for |
|---|---|---|
| `local` **(default, Raka's setup)** | `SEHATY_MEDIA=/var/lib/sehaty/media` | one server you own |
| `s3` | `SEHATY_S3_BUCKET`, `SEHATY_S3_ENDPOINT`, credentials | multi-user, or hosted |

**S3 is DEFERRED (10 Sep).** The interface stays because it is a cheap seam, but only
`local` is built and S3 is explicitly not being designed around. Raka: *"gocryptfs can't
travel only for localfile / s3 we didn't need to think about it."* Revisit if someone
actually needs hosted storage.

**Content-addressed either way.** The key is the SHA-256 of the bytes, so the same photo
sent twice stores once, and `food_log.photo_hash` points at it. Content addressing is also
what makes the backends interchangeable — nothing depends on a path shape, so switching
later is a config change rather than a migration.

**The live SQLite stays on local disk regardless** — `/var/lib/sehaty/sehaty.db`, WAL mode.
It must never sit on a network filesystem: SQLite's locking is unreliable there, documented
upstream, and a known corruption path rather than a theoretical one. A health log that
silently corrupts is worse than one that is merely un-backed-up.

**The database is already backed up** with no extra machinery: `srvdev01` — the box that RUNS it — is CT 105 on pve01, and the
nightly vzdump on pve01 is `all 1`, so the container — SQLite included — reaches the NAS at
02:30.

**Media writes must never block a log entry.** If the store is unreachable, the set or the
meal is still recorded and the media is queued for retry. A missed photo must not cost you
the logged meal.

## 8c. Encryption at rest — DECIDED 10 Sep

**The whole database file is encrypted, not just document bodies.**

The first implementation encrypted only documents, because `modernc.org/sqlite` (cgo-free)
has no SQLCipher and the LXC containers have no FUSE for `gocryptfs`. That left weight
values, food entries, training notes and profile goals in **plaintext** inside a file that
ships to the NAS nightly. Demonstrated, not assumed: `grep SECRETNOTE sehaty.db` found it.

**Fixed by changing driver, not schema.** `github.com/ncruces/go-sqlite3` is the real
SQLite compiled to WebAssembly and translated to Go — still cgo-free, still `database/sql`,
still one static binary — and it ships an **Adiantum VFS** that encrypts every 4 KiB page.
All the SQL survived; only `storage.Open` changed.

| layer | cipher | protects | authenticated? |
|---|---|---|---|
| database file (incl. WAL) | Adiantum (XChaCha12 + AES + NH/Poly1305) | every table | **no** — length-preserving |
| document bodies | AES-256-GCM, AAD-bound to profile/key/version | clinical + prescriptive text | **yes** |

**The second layer is not redundant.** Adiantum hides content but cannot detect tampering,
and cannot stop a ciphertext being *moved*. The AAD binding does both, which is why
documents keep their own envelope inside the encrypted file.

**Two subkeys, never one.** `SEHATY_KEY` is a master; the file key and the document key are
independent HKDF-SHA256 expansions of it (`sehaty:db:adiantum:v1`,
`sehaty:doc:aes256gcm:v1`). Handing the same bytes to two different constructions is the
classic key-reuse mistake. Derivation is deterministic — a random salt would make the
database unopenable after the first restart.

**What it does not defend.** The key is in the server's environment, so a running server can
always decrypt. This protects **backups, a stolen disk, and a copied container image**. It
does not protect against someone who has compromised the running process. That limit is the
price of Sehaty sending a weekly review without anyone typing a passphrase.

**Two consequences to accept:**
- `sqlite3 sehaty.db` no longer works — the file is unreadable without the key, including
  during debugging. Wrong key reads as `file is not a database`.
- **A lost key is unrecoverable.** There is no reset. Back it up somewhere that is not the
  server it protects.

## 8d. Paths and file mapping

**One rule:** everything mutable lives under **one root**, so "back up Sehaty" is a single
path — and the **key lives outside that root**, so backing up Sehaty never backs up the
means to read it. `sehaty` **refuses to start** if `SEHATY_KEY_FILE` resolves inside
`SEHATY_DATA` (`TestKeyInsideDataDirIsRefused`). This is checked rather than documented and
hoped for, because it is easy to get wrong and impossible to notice.

| env | default | holds | in the backup? |
|---|---|---|---|
| `SEHATY_DATA` | `/var/lib/sehaty` | root of all mutable state | **yes** |
| `SEHATY_DB` | `$SEHATY_DATA/sehaty.db` | encrypted SQLite + `-wal`, `-shm` | yes |
| `SEHATY_MEDIA` | `$SEHATY_DATA/media` | voice notes, meal photos | yes |
| `SEHATY_KEY_FILE` | `/etc/sehaty/key` | master key, mode `0400` | **NO — must not be** |
| `SEHATY_EXERCISES` | `/opt/sehaty/exercises.json` | read-only dataset | no — ships with build |

Docker maps the same shape: `SEHATY_DATA=/data` (a volume), key at
`/run/secrets/sehaty_key` (tmpfs), dataset bind-mounted read-only.

**Media file mapping:**

```
$SEHATY_MEDIA/<profile_id>/<kind>/<ab>/<sha256>
                                └ kind ∈ {photo, voice}
                                       └ <ab> = first two hex digits of <sha256>
```

- `<profile_id>` is constrained by `storage.ValidID` to `^[a-z0-9][a-z0-9_-]{0,30}$`.
  The id becomes a **directory name**, so an unchecked id here is a path-traversal bug.
- `<sha256>` is the hash of the **plaintext** bytes, so the same photo sent twice stores
  once and `food_log.photo_hash` points at it.
- `<ab>` shards the directory so no one directory grows to hundreds of thousands of entries.

**Media encryption — DONE 10 Sep, in two layers.**

*Layer 1, in the application (`internal/media`).* Every blob is sealed with AES-256-GCM
under a third HKDF subkey (`sehaty:media:aes256gcm:v1`), AAD-bound to `profile_id|kind|hash`
so a file moved into another profile's directory becomes undecryptable rather than readable.
The content hash is of the **plaintext**, not the ciphertext — GCM uses a fresh nonce per
seal, so hashing the ciphertext would store the same photo twice and break deduplication.
This layer travels: it works identically on Docker, on macOS, and for anyone who is not Raka.

*Layer 2, gocryptfs (`srvdev01` only).* Mounted over `media/` **and nothing else**.

```
/var/lib/sehaty/
├── sehaty.db        Adiantum, on REAL DISK — deliberately not under FUSE
├── media.enc/       gocryptfs ciphertext   ← what vzdump actually backs up
└── media/           gocryptfs mount        ← SEHATY_MEDIA, the plaintext view
```

**Why not mount the whole data root:** that would put SQLite on a userspace filesystem for
no gain. The database is already encrypted by Adiantum, and adding FUSE beneath it trades a
known-good locking path for an untested one. §8b already forbids SQLite on exotic
filesystems; this honours it.

**What layer 2 adds that layer 1 cannot:** filenames. Content addressing leaves
`<profile_id>/photo/ab/<sha256>` visible on disk, so a stolen backup would reveal *who* has
a Sehaty profile and how many photos each has. gocryptfs hides that — `raka` becomes
`kNz7SWmq9wEFY_T2HpziNw`. Verified, not assumed.

**The failure mode that matters** is a mount that does not come up: sehaty would then write
into a bare directory. Two guards. The blobs are *already* encrypted by layer 1, so contents
never leak — that is the concrete payoff of running both. And the bare mountpoint is
`root:root 0500`, so the `sehaty` user is refused outright:

```
touch: cannot touch '/var/lib/sehaty/media/leaked': Permission denied
```

`sehaty.service` declares `Requires=sehaty-media.service`, so it will not start without the
mount. The passphrase is `/etc/sehaty/gocryptfs.pw` (0400) — outside `SEHATY_DATA`, same rule
as the master key, and for the same reason.

**Requires FUSE**, which unprivileged LXC does not give you by default:
`pct set 105 --features nesting=1,fuse=1` plus a container reboot. bookworm ships only
`fusermount3`; gocryptfs 2.3 needs the FUSE-2 helper, so `apt install fuse` is required too.
